# Smart Workspace Bar and Export Centre boundaries

The workspace bar reads centre display name, branch and logo from the existing device-local `BrandingProvider`; it reads the role from `AppShell`'s explicit presentation prop, which currently defaults to the demo Admin role. The branch is display-only. No switcher, sign-in, backend search, student search or role verification is implemented. The command registry includes only routes with a real `href` in `roleFeatures` and the existing `/students/new` preview action for Admin and Manager. Planned null-href role entries are excluded.

The `roleFeatures`, `workspaceCommands` and `exportChoices` registries control presentation only. A browser user can alter client state, so none of these is an authorization boundary. Platform Owner and Student get no administrative export. Teacher sees only assigned-batch report categories, but those actions remain unavailable until server-verified teacher assignments and report data exist. Admin and Manager see the same local fictional demo student directory export; this does not establish Manager centre grants.

The enabled demo exports are a student directory and batch-wise student lists, both CSVs generated from the existing `students` fictional fixture array. They include only student name, batch and status, have `DEMO DATA` in the first row and filename, and use CSV quoting plus an apostrophe prefix for values that could be interpreted as spreadsheet formulas. They make no network request and read no newly entered form draft. Excel and PDF are disabled because no implementation or supporting package exists. Admissions, fees, attendance, tests/results, homework, staff and operational exports are unavailable because the project has no corresponding record source. Empty filtered results produce a labelled, header-only demo CSV.

Before enabling institutional exports, implement a server-side export endpoint or trusted job that derives the signed-in user and tenant from verified authentication, checks a specific export permission for the requested centre and report, applies batch assignments for Teachers, and revalidates filters server-side. Do not trust a tenant, role, batch ID, student list or permission supplied by the browser. Require an audit event containing the actor, tenant, report type, filters, row count, outcome and timestamp without copying report contents into logs. Apply least-data field allowlists, bounded date ranges, row/size limits, CSV formula defenses, and short-lived authorized download URLs for large asynchronous exports. Keep Platform Owner platform reports separate from centre student records and never infer cross-centre student permission from that role.

## Appearance refresh trace

The root layout reads the appearance cookie for the SSR snapshot and server markup. Its inline head bootstrap reads the two appearance localStorage keys before body parsing, writes root theme attributes and mirrors the saved projection into a cookie. When the cookie snapshot differs from localStorage it requests one navigation (guarded in sessionStorage) so the next server render can use the mirror. During hydration, `Providers` intentionally supplies the cookie-derived server snapshot; after hydration `useSyncExternalStore` restores localStorage. Thus a matching cookie/storage pair produces the same selected scene for server and first client render. A stale cookie can produce a server markup/source mismatch until reconciliation navigation; browser paint timing across that navigation remains browser-specific.

The scene is server-rendered from that snapshot. Topography and Chroma are CSS immediately. Photo uses a local image element; it previously had default Next Image lazy loading, so the CSS base (`#11191a`) could remain visible before the image was fetched/decoded. It now requests eager/high-priority loading when Photo is the selected scene. Motion renders a local video with a local photo poster and `preload="metadata"`; playback begins after hydration and media policy checks. Its video now has the `landing-backdrop__video` class expected by the OpenGlass-adapted sizing/filter rules. The poster/base remain a plausible dark photographic fallback before the first decoded video frame. Custom image/video data is restored asynchronously from IndexedDB and retains its existing local gradient fallback.

The in-app Chromium DOM/hydration traces in `docs/brave-refresh-investigation.md` did not reproduce the reported Brave flash and do not capture compositor frames. The source fixes above address identified media readiness/style gaps; they do not prove that Brave's reported flash is eliminated. Brave's profile, Shields, cache behavior and earliest compositor frame still require verification in that browser.
